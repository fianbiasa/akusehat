# Security Audit — Phase 13

Conducted 2026-07-30 against the OWASP Top 10 checklist in [04-Architecture.md](04-Architecture.md) §8. This is a point-in-time audit against the codebase as of Phase 13; re-run the systematic checks below whenever a new controller/route is added, not just at major milestones.

## Findings

| Concern | Status | Notes |
|---|---|---|
| Broken access control | ✅ Verified | Spot-audited a representative sample across every module built so far (Profile, Programs, Coach, Onboarding, Admin) — every controller action touching a route-bound model checks ownership/assignment (`abort_unless($x->user_id === $request->user()->id, 403)` or the `AuthorizesProgramAccess`/`ResolvesTargetUser`/coach-assignment-check patterns). `DailyTaskController`/`ChecklistItemController::update()` deliberately restrict to the owning Member only (not the assigned Coach) — completing a checklist item is inherently a "did I do this today" action, not something a Coach should be able to do on a Member's behalf. |
| API key exposure | ✅ Verified | `UserAiSetting::$hidden = ['api_key_encrypted']`. Admin's platform-default AI settings page (`/admin/settings`) only ever returns `has_api_key: bool`, never the key or its encrypted form. |
| Injection | ✅ Verified | Eloquent/query builder used throughout. Only one `DB::raw()` call in the codebase (`PruneAIMemoryRelevanceJob`), and it interpolates a class constant (`self::DECAY_FACTOR`), never user input. |
| SSRF via local AI providers | ✅ By design | `ai_providers.base_url` is only ever set by an Admin (`Admin\AiProviderController`, `ai.manage`-gated) — never accepted from a Member's per-request input. No separate host allowlist exists beyond "only a fully-trusted Admin account can set this at all," which matches the documented mitigation's actual intent (trusted-Admin-configured, not member-supplied) — Admins already hold far more dangerous capabilities elsewhere in this system (user/role management), so this isn't a new trust boundary. |
| Sensitive data exposure | ✅ Verified | Grepped every `Log::*` call in `app/` — the only ones are `AIGatewayService::logFailure()`, which logs `user_id`/`provider_id`/`purpose`/the exception message only, never health data or request payloads. `ai_request_logs.request_payload` (which does include prompt text derived from health data) is a DB table, not an application log file — access to it is Admin-only. |
| CSRF | ✅ Verified | Laravel's default `VerifyCsrfToken` middleware active on the `web` group (unmodified from framework default). |
| Rate limiting | ✅ Added this phase | `POST /login` already had Laravel Breeze's own per-email+IP limiter (5/min) built in. Added route-level `throttle` to: `POST /register` (5/min), `POST /forgot-password` (3/min, stricter since every attempt sends a real email), `POST /ai/settings/{id}/test` (10/min, fires a real provider request), `POST /conversations/{id}/messages` (20/min, triggers a real synchronous AI call for `ai_assistant` conversations), `POST /user-programs` and `.../regenerate` (5/min each, both dispatch AI-calling jobs). |
| File upload | ✅ Verified | Only one upload surface in the app: `ProgressPhotoController` — `image` MIME validation, 5MB cap, stored on the `local` disk (outside the public web root), served only via 30-minute signed URLs. |
| Mass assignment | ✅ Verified | Explicit `$fillable` on every model; framework-managed columns (`onboarding_completed_at`, `email_verified_at`, `last_login_at`) deliberately excluded from `$fillable` and set via `forceFill()` at the specific call sites that legitimately need to. This exact guard is what caught a real bug in Phase 9 (`Admin\UserController::store()` silently failing to set `email_verified_at` via plain `create()`) — the mass-assignment protection was working correctly; the bug was a call site not using the established `forceFill()` pattern. |
| XSS | ✅ Verified | React auto-escapes by default. The only `dangerouslySetInnerHTML` usage in the codebase (3 Admin list pages) renders Laravel's own paginator `link.label` values (`&laquo; Previous`, page numbers) — framework-generated HTML entities, never user-supplied content. |
| Dependency security | ⚠️ Partial | `composer audit`: no advisories found, but this environment has no outbound network access to Packagist, so the check ran against a local cache that may be stale — re-run with live network access before launch. `npm audit`: 6 high-severity advisories, all in the `eslint`/`minimatch`/`brace-expansion` dev-tooling chain (`eslint-plugin-react` → `@eslint/eslintrc` → `minimatch` → `brace-expansion`, a DoS-via-unbounded-expansion issue). This is a **devDependency only** — never shipped to production, never executed by real users — so it doesn't affect the deployed app's attack surface. The fix (`npm audit fix --force`) is a breaking ESLint 9→10 major-version bump; deferred rather than applied automatically, since a lint-tooling breakage isn't itself a runtime security issue and warrants a deliberate, tested upgrade rather than a forced one. |

## Follow-ups for a future security pass
- Re-run `composer audit` with live network access before public launch.
- Plan the ESLint 10.x upgrade separately (breaking change to devDependencies, not urgent).
- This audit did not attempt automated penetration testing (SQLi/XSS fuzzing, auth bypass fuzzing) — a pre-launch pass with a dedicated tool (e.g. OWASP ZAP) against a staging environment is recommended per the original Phase 14 (QA & Launch) scope.
