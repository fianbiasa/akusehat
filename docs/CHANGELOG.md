### Phase 7 — Progress Tracking & Health Score (2026-07-30)
- Migrations for `weight_logs`, `waist_logs`, `body_fat_logs`, `sleep_logs` (all unique-per-user-per-day), `water_intake_logs`/`progress_photos` (multiple per day), and `health_scores`. `weight_logs`/`waist_logs` now supersede `body_measurements` (Phase 3) as the primary weight/waist source, fulfilling the forward-looking comment left in Phase 3's `HealthProfileService`.
- `HealthScoreService`: the documented 8-component weighted formula (BMI, waist, sleep, water, activity, weight trend, checklist consistency, disease-management adherence) from docs/08-Knowledge-Base.md §5. The doc names each component's weight and "basis" but not an exact scoring curve, so each component's decay function is designed and documented inline — e.g. BMI loses 2 points per unit outside the 18.5-24.9 healthy range; waist uses IDF Asian-population cutoffs (male <90cm/female <80cm) relevant to this app's Indonesian userbase; disease-management adherence is proxied via `meal_plans.is_completed` since there's no per-meal "what did you actually eat" logging in this app, defaulting to full marks when a user has no active disease restrictions to manage. 17 unit tests pin every component against known, hand-calculated inputs.
- `ComputeHealthScoreJob` (daily, all onboarded users) computes the score then asks the `analyze()` AI capability (new `health_score_explain` prompt template) to narrate it in plain language — explicitly instructed to explain, never recompute, the deterministic score. Falls back to a deterministic "your weakest component is X" explanation when no AI provider is available, matching every other AI-touching job in this app.
- Full CRUD API for weight/waist/body-fat/sleep/water/photos/health-score (§7 of 05-API-Specification.md), with M/C/A access via a `?user_id=` query param checked against `user_programs.coach_id` — the same pattern the Programs module already used, ahead of Phase 8's proper coach-assignment UI.
- Progress photos: stored on the `local` disk (`storage/app/private`, never web-accessible) regardless of privacy setting, served only through a 30-minute temporary signed URL. `is_private` toggling doubles as the wireframe's "Bagikan ke Coach" mechanism — no separate sharing column needed.
- Member Progress page (`/progress`) per wireframe/progress.md: Health Score trend (tap a point to read that day's explanation), weight/waist mini-charts with quick-log dialogs, sleep/water 7-day averages, a photo timeline with upload/share/delete, and a 14-day checklist consistency grid. The Minggu/Bulan/90-Hari range selector filters an already-loaded 90-day dataset client-side instead of re-querying per range — added `recharts` for the charts (no shadcn chart wrapper existed yet). Health Score card also added to the Dashboard, deferred from Phase 6 pending this phase's tables.
- Two bugs fixed, both pre-existing (not introduced this phase) and both found via live HTTP smoke testing: (1) the same weight-source fallback chain (`weight_logs` → `body_measurements` → `health_profiles.initial_weight_kg`) was independently duplicated across `HealthProfileService`, `RuleEngineService`, `PromptBuilderService`, `AIMemoryService`, and `DashboardController` — consolidated into `User::latestWeightKg()`/`latestWaistCm()` rather than adding a fifth copy while wiring in the new tables. (2) Manually rebuilding a response array from a date-cast Eloquent attribute (`['start_date' => $model->start_date]`) silently bypasses the `'date:Y-m-d'` cast format, since that format is only honored by the model's own `toArray()`/`toJson()` — Carbon's default JSON serialization (a full UTC-shifted ISO8601 timestamp) takes over instead. Found on `ProgressPhotoController`, `ProgressPageController`, and `DashboardController`; fixed with explicit `->toDateString()` calls, each with a regression test. Notably this is pure PHP/Carbon behavior, not a MySQL-vs-SQLite difference, so once the missing assertions were written the bug reproduced identically under the PHPUnit suite's SQLite connection — it simply hadn't been asserted for before.
- 238/238 tests passing (51 new for Phase 7, including 3 regression tests for the date-serialization bug).

### Phase 6 — Program Generation (2026-07-30)
- Migrations for `programs`, `user_programs`, `program_goals`, `weekly_plans`, `daily_tasks`, `meal_plans`/`meal_plan_items`, `workout_plans`/`workout_plan_items`, `checklist_items`, `reminders`, plus the stock `notifications` table and a follow-up migration finally adding the `ai_memories`/`ai_recommendations.user_program_id` foreign keys Phase 5 deferred until this table existed. `weekly_plans` also gets a `viewed_at` column (not in `mysql.sql`) to support the dashboard's "Weekly Review card disappears once viewed" behavior.
- `ProgramGenerationService`: Goal → Rule Engine → `AIGatewayService` (`generatePlan` capability, reusing Phase 5's `meal_plan`/`workout_plan` templates) → persist. Generates **one day at a time** rather than the full 90 days upfront — a plan that's meant to adapt weekly has no reason to pre-generate months of content that will likely be superseded, and doing so would mean 180+ AI calls just to start a program. Falls back to a deterministic Rule-Engine-only plan (picked directly from `kb_foods`/`kb_exercises`) whenever no AI provider is configured or all configured providers fail.
- `GenerateProgramJob` (queued, dispatched from onboarding completion and the `/regenerate` endpoint) + a cache-backed generation-status endpoint (no schema column reserved for this ephemeral state).
- `AIMemoryService`: deterministic milestone/concern/pattern/trend detection from checklist completion and weight history (7 fully-completed days → milestone, 3 zero-completion days → concern, low workout adherence vs. high meal adherence → pattern, ≥0.5kg 14-day weight change → trend). `ScanAIMemoryJob` (daily) and `PruneAIMemoryRelevanceJob` (weekly relevance decay) scheduled; also invoked incrementally on every checklist/task check-in.
- `RecommendationApplierService`: only `habit`/`motivation` weekly-review adjustments ever auto-apply, even when the AI marks a `meal_adjustment`/`workout_adjustment` as `auto_applicable` — the AI's `detail` field is free text, not a structured delta, so there's no sound way to bounds-check a mutation to `meal_plan_items`/`workout_plan_items` against it. Structural adjustments always go to Coach approval instead of trusting a fabricated text-parsing heuristic.
- `GenerateWeeklyReviewJob`, dispatched by a daily scheduler tick that finds whichever programs' current week just ended (a program's week boundary is relative to its own `start_date`, not a shared calendar day).
- `DispatchRemindersJob` (every minute, timezone-aware via `users.timezone`, `last_sent_at` as the once-per-day dedup guard) delivering reminders as in-app database notifications (the dashboard's 🔔 bell). Onboarding's 4 reminder-time answers (water/meal/workout/check-in) now actually create `reminders` rows, and its target-weight/timeframe/notes answers now create the program's `program_goals` row — both previously-collected-but-unused pieces of onboarding data.
- Member Dashboard (today view) per wireframe/dashboard.md: program progress card, latest weight, today's checklist (togglable), new-weekly-review card, multi-program switcher. Health Score card is deferred to Phase 7 (`health_scores` doesn't exist yet) rather than faked. Program detail and weekly-review detail pages added.
- Events `ProgramGenerated` → in-app "program ready" notification, `CheckInSubmitted` → incremental AI Memory scan, `AIRecommendationCreated` → coach notification (checks `user_programs.coach_id`, which exists now even though Phase 8's coach-assignment UI doesn't yet — safely a no-op until then).
- Two bugs found by live HTTP smoke testing — pre-existing in Phase 3's onboarding code, not introduced this phase, but only reachable once a real program-generation flow exercised onboarding completion end-to-end against real MySQL: (1) `HealthProfileService`'s BMI/BMR/TDEE math has no input sanity bounds, so an unrealistic height (e.g. a typo) produces a BMI that overflows `health_profiles.bmi`'s `DECIMAL(5,2)` under MySQL's strict mode — invisible against the test suite's SQLite, which doesn't enforce DECIMAL range at all. (2) A "repeatable" onboarding question (medications/allergies) had no server-side check that its answer was actually an array, so a plain-string answer crashed `MapOnboardingAnswersToHealthProfile::mapRepeatable()` with a `TypeError`. Both fixed with boundary validation in `OnboardingController::answer()` (min/max bounds sourced from `onboarding_questions.validation_rules` for the 5 body-measurement questions, an `array` rule for repeatable questions), each with a regression test.
- 184/184 tests passing (32 new for Phase 6, 2 new onboarding regression tests for the bugs above).

### Phase 5 — AI Provider Layer (2026-07-29)
- Migrations/models for `ai_providers`, `ai_models`, `user_ai_settings`, `ai_prompt_templates`, `ai_memories`, `ai_recommendations`, `ai_request_logs`. `user_ai_settings` intentionally drops `mysql.sql`'s literal `UNIQUE(user_id, is_default)` index — MySQL has no partial/filtered unique index, so a plain 2-column unique also caps *non*-default rows at one per user, which breaks FR-AI-06's requirement for a second (failover) provider per user. "One default per user" is enforced app-side instead: every write path that sets `is_default = true` unsets the others in the same transaction.
- `AIProviderInterface` (7 methods: `analyze`, `chat`, `generatePlan`, `weeklyReview`, `dailyMotivation`, `mealSuggestion`, `workoutSuggestion`) with 6 adapters — `OpenAIProvider`, `ClaudeProvider`, `GroqProvider`, `GeminiProvider`, `OllamaProvider`, `LMStudioProvider` — sharing a common `AbstractHttpProvider` base (JSON decoding with brace-extraction fallback, transport-error → `AIProviderException` mapping). `AIProviderFactory` resolves each provider's `driver_class` column to a concrete instance at runtime.
- `PromptBuilderService`: resolves `{{variable}}` placeholders per template (user profile, Rule Engine output, KB context, AI memory context, progress snapshot, etc.) against the seeded `prompts/*.txt` templates; the fixed JSON-output instruction block lives in the template text itself rather than being appended separately.
- `AIResponseProcessor`: up to 2 corrective retries on invalid JSON or failed schema validation (via a custom lightweight `JsonSchemaValidator`), falling back to Rule-Engine-only output plus an audit `ai_recommendations` row if all attempts are exhausted.
- `AIGatewayService`: resolves the user's default provider, times and logs every call to `ai_request_logs`, and fails over to a secondary configured provider on transport error — both the primary's failure *and* the secondary's outcome are logged (a gap caught during manual verification: failover succeeding was silently swallowing the primary's failed attempt).
- Member Settings → "AI Provider" (`/ai/settings`): CRUD for provider/model/API key/temperature (API key stored `Crypt::encryptString()`'d, never exposed back to the page), "Test Connection" (a direct provider call bypassing the retry/validation pipeline), "Jadikan Default". Shown as a list of configured providers rather than the wireframe's single radio group, since failover requires more than one saved provider at once.
- Admin → "AI Providers" (`/admin/ai/providers`): provider active/inactive toggle, per-provider model CRUD.
- Two bugs caught by live HTTP smoke testing (not the in-process test suite): (1) `GeminiProvider` chained `->withQueryParameters(['key' => ...])` after `->post()` instead of before, silently making it a no-op on the response object rather than the request. (2) `AiSettingsController::validated()` read `$validated['api_key']` without a null-coalesce — fine when the form always sends the field (as every PHPUnit test did), but a real request that omits `api_key` entirely (valid for local providers like Ollama that need no key) threw an "Undefined array key" 500. Both fixed; the second got a regression test.
- 150/150 tests passing (added 1 regression test for the missing-`api_key` bug). Deferred to a later phase: Admin Prompt Template editor UI, Admin AI request-log viewer/cost dashboard, and a real-provider integration test (no API keys/local model server available in this environment — covered instead by `Http::fake()` tests plus a live smoke test against the real OpenAI API with an invalid key and a local Ollama endpoint with nothing listening, both of which degraded gracefully).

### Phase 4 — Knowledge Base & Rule Engine (2026-07-29)
- Migrations/models for `kb_foods`, `kb_exercises`, `kb_nutrition_articles`, `kb_faqs`, `rule_engine_rules` (`kb_diseases` was already done in Phase 3).
- Starter/demo KB content — 40 foods, 28 exercises, 3 articles, 3 FAQs — explicitly **not** the full ~300–500-row SME/TKPI-sourced catalog docs/08-Knowledge-Base.md §7 calls for; per PRD §6.3, full content curation is a product-owner/SME task, not something to fabricate wholesale. Every seeded food's `source` field flags it as pending review.
- `RuleEngineConditionEvaluator`: a constrained DSL interpreter (`>=`,`<=`,`>`,`<`,`==`,`in`,`and`,`or`,`not`), never `eval()`'d, per 04-Architecture.md §8. A missing/null context field never matches (fails closed, not open).
- `RuleEngineService::evaluate(User): array` — the fixed 5-key output contract from 08-Knowledge-Base.md §3.3. Within a category, same-key conflicts resolve by priority (higher wins); `disease_restriction` is the one category that **unions** instead — two conditions mean two sets of restrictions apply, not just the higher-priority one's.
- Seeded 11 baseline rules across all 5 categories, including the doc's 3 worked examples verbatim. Full pipeline verified against realistic profiles both in unit tests and live: a 33.2-BMI diabetic sedentary user correctly gets a 25%-deficit calorie target (obese threshold overriding the plain overweight rule), a diabetes-adjusted macro split, `beginner` workout level, and a `low_glycemic_index` restriction — matching manual calculation exactly.
- Read-only KB search endpoints (`GET /kb/foods|exercises|diseases|articles|faqs`, `?q=&category=&tags[]=`). Admin CRUD for editing this content is deferred (only Rule Engine has an Admin UI so far).
- Admin Rule Engine CRUD + "Uji Coba" — dry-runs a rule's condition against a hand-entered sample profile without touching a real user, showing whether it matches and what action would apply.
- 110/110 tests passing, including a full worked-example integration test matching 08-Knowledge-Base.md §3.3's documented output shape exactly.

### Phase 3 — Health Profile (2026-07-29)
- Migrations/models for `health_profiles`, `lifestyle_profiles`, `user_diseases`, `user_allergies`, `user_medications`, `body_measurements`, plus `kb_diseases` pulled forward from Phase 4 (only that one KB table + a 5-row seed, since `user_diseases.kb_disease_id` is a required FK — kb_foods/kb_exercises/kb_nutrition_articles/kb_faqs and their Admin CRUD stay in Phase 4).
- `HealthProfileService`: BMI/BMR (Mifflin-St Jeor)/TDEE, verified against the worked example in docs/07-Prompt-Engineering.md §4 (age 39/167cm/77.5kg → BMI 27.79, BMR 1628.75, TDEE 2239.53 at "light" activity).
- Weight source precedence: most recent `body_measurements` row over `health_profiles.initial_weight_kg` (the onboarding-time baseline) — `weight_logs` (Phase 7) will become the primary trigger once it exists.
- `BodyMeasurementObserver`/`LifestyleProfileObserver` recalculate BMI/BMR/TDEE automatically on a new measurement or an `activity_level` change.
- `MapOnboardingAnswersToHealthProfile` listener populates all six tables from the 55 onboarding answers, matched by `onboarding_questions.step` (coupled to `OnboardingQuestionSeeder` — documented inline since the mapping breaks silently if the two drift apart).
- Settings → "Kesehatan" page (`/profile/health`): editable health/lifestyle fields, disease/allergy/medication add-remove, and a measurement log — all Member-own-data only; Coach/Admin read access is deferred to Phase 8 (`coach_members` doesn't exist yet).
- Two real bugs caught by live HTTP smoke testing (not the in-process test suite): (1) Laravel 12's `Application::configure()` auto-discovers `app/Listeners` by convention, which was silently double-registering every explicitly-`Event::listen()`'d listener (2 listeners → 4 registered) and caused a duplicate-insert crash under concurrent-looking execution — fixed with `->withEvents(discover: false)` in `bootstrap/app.php` so registration order in `AppServiceProvider` is the only source of truth. (2) `date`-cast fields (`date_of_birth`, `measured_at`, etc.) serialize to JSON as full UTC-shifted ISO8601 timestamps by default, which silently breaks `<input type="date">` and can shift the date by a day relative to `APP_TIMEZONE` — fixed with the `date:Y-m-d` cast format across every date-only column.
- 68/68 tests passing (added BMI/BMR/TDEE unit tests, onboarding-mapping feature tests, and profile API CRUD feature tests).

### Decisions Locked In (from product discussion)
- Platform positioning: **AI Personal Health Coach**, not a diet-only app; "Diet & Transformasi 90 Hari" is module 1 of an extensible platform.
- Architecture: Rule Engine + Knowledge Base compute deterministic ground truth; AI reasons over it and returns JSON only, validated against a schema before persistence or display.
- Stack: Laravel 12, PHP 8.4, Inertia + React, TailwindCSS + ShadCN, MySQL, Queue + Scheduler.
- Roles: Admin, Coach, Member.
- AI may auto-adjust programs within Rule-Engine-defined bounds; out-of-bounds changes require Coach approval.
- Users may run multiple programs concurrently/sequentially.
- Multi-provider AI support (OpenAI, Claude, Groq, Gemini, Ollama, LM Studio) via a shared `AIProviderInterface`, user-configurable per account.
