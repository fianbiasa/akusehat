# Backup & Restore Runbook

Covers the two things this app can't regenerate if lost: the MariaDB database (`db_akusehatwebid`) and the private object storage disk (progress photos, data exports). Written 2026-07-30 against the live server this app is deployed on.

**No automated backup currently runs anywhere on this server** (checked `crontab -l` for root and every site's cron, `/etc/cron.d`, `/etc/cron.daily` — nothing mysqldump- or backup-related exists for *any* site on this box, not just AkuSehat). This runbook documents the manual procedure and proposes an automation script; actually enabling scheduled automated backups is a decision left to the user (it involves retention policy and where backups get stored — ideally off this same server/disk, which needs credentials/access this session doesn't have and shouldn't unilaterally provision).

## What needs backing up

| What | Where | Why |
|---|---|---|
| MariaDB database | `db_akusehatwebid` (all application data — users, programs, health data, everything) | Everything. Full loss = full data loss. |
| Private object storage | `storage/app/private/` (progress photos under `progress-photos/`, data exports under `data-exports/`) | User-uploaded/generated files not stored in the DB. |
| `.env` | Repo root (gitignored, never in version control) | Without it the app can't even boot — DB/Redis/mail credentials, `APP_KEY` (losing this makes every `Crypt::encryptString()`'d value, e.g. AI provider API keys, permanently undecryptable). |

Not backed up / not needed:
- `storage/logs/*` — operational logs, not user data.
- Redis — used for cache/sessions/queue only, no data that isn't reconstructible or already durably in MySQL. RDB snapshotting is enabled server-wide (`save 3600 1 300 100 60 10000`, confirmed via `redis-cli CONFIG GET save`) but `appendonly` is off, so a Redis crash can lose queued-but-unprocessed jobs since the last snapshot — acceptable for this app's queue (jobs are cheap to re-trigger; nothing in the queue is the sole copy of anything).
- `public/build/` — regenerated by `npm run build` from source, not data.

## Manual backup

```bash
# Database — run as any user with SELECT access; credentials are in .env, never hardcode them in a script committed to the repo
mysqldump --single-transaction --quick \
  -h 127.0.0.1 -u u_akusehatwebid -p db_akusehatwebid \
  | gzip > akusehat-db-$(date +%Y%m%d-%H%M%S).sql.gz
# (enter DB_PASSWORD from .env when prompted)

# Private storage
tar -czf akusehat-storage-$(date +%Y%m%d-%H%M%S).tar.gz \
  -C /var/www/html/akusehat.web.id/storage/app private

# .env — copy somewhere safe manually, do not commit or leave world-readable
cp /var/www/html/akusehat.web.id/.env ~/akusehat-env-backup-$(date +%Y%m%d)
```

`--single-transaction` takes a consistent InnoDB snapshot without locking tables — safe to run against the live database without downtime.

## Manual restore

```bash
# Database (drops and recreates all data currently in db_akusehatwebid — confirm you actually want this first)
gunzip < akusehat-db-YYYYMMDD-HHMMSS.sql.gz | mysql -h 127.0.0.1 -u u_akusehatwebid -p db_akusehatwebid

# Private storage
tar -xzf akusehat-storage-YYYYMMDD-HHMMSS.tar.gz -C /var/www/html/akusehat.web.id/storage/app
chown -R www-data:www-data /var/www/html/akusehat.web.id/storage/app/private

# .env
cp ~/akusehat-env-backup-YYYYMMDD /var/www/html/akusehat.web.id/.env
chown www-data:www-data /var/www/html/akusehat.web.id/.env && chmod 640 /var/www/html/akusehat.web.id/.env

# After any restore, clear cached config/routes so the app picks everything up cleanly
cd /var/www/html/akusehat.web.id
sudo -u www-data php artisan config:clear
sudo -u www-data php artisan cache:clear
```

**Verify after restoring**: log in as an existing user, check `/dashboard` renders real data, check an existing progress photo loads (proves both the DB row and the storage file restored consistently — a DB backup and storage backup taken at different times will have mismatched `progress_photos.photo_path` rows vs. actual files).

## Proposed automation (not yet enabled)

A daily cron-driven backup, following this box's existing pattern of Supervisor/cron entries per-site (see `/etc/supervisor/conf.d/akusehat-worker.conf` from the Phase 13 load test work). **Do not enable this without first deciding where backups are stored** — writing backups to the same disk as the database they're backing up protects against accidental `DROP TABLE`/bad migration, but not against disk failure or the box itself being compromised; offsite storage (S3-compatible bucket, a different server, etc.) is the actual goal for anything launch-worthy.

```bash
#!/bin/bash
# /var/www/html/akusehat.web.id/scripts/backup.sh (example — not installed)
set -euo pipefail
BACKUP_DIR="/var/backups/akusehat"  # should be OUTSIDE the web root and ideally on different physical storage
RETENTION_DAYS=14
TIMESTAMP=$(date +%Y%m%d-%H%M%S)

mkdir -p "$BACKUP_DIR"
source /var/www/html/akusehat.web.id/.env  # for DB_PASSWORD - keep this script's own permissions locked down (600, root-only)

mysqldump --single-transaction --quick -h 127.0.0.1 -u "$DB_USERNAME" -p"$DB_PASSWORD" "$DB_DATABASE" \
  | gzip > "$BACKUP_DIR/db-$TIMESTAMP.sql.gz"

tar -czf "$BACKUP_DIR/storage-$TIMESTAMP.tar.gz" -C /var/www/html/akusehat.web.id/storage/app private

find "$BACKUP_DIR" -name '*.gz' -mtime +$RETENTION_DAYS -delete
```

Cron entry (matching the format already used elsewhere in `www-data`'s crontab on this box):
```
0 3 * * * /var/www/html/akusehat.web.id/scripts/backup.sh >> /var/www/html/akusehat.web.id/storage/logs/backup.log 2>&1
```

## Follow-ups before launch
- Decide on and provision offsite backup storage (S3-compatible bucket is the common choice; Laravel's `league/flysystem-aws-s3-v3` package would let the same disk abstraction already used for `local` storage push a copy there directly).
- Enable the automation above (or an equivalent) once offsite storage exists.
- Actually rehearse a full restore on a non-production copy at least once before launch — an untested backup is not a backup.
